     Conditional Survey Branching — Implementation Plan

     Context

     The platform needs conditional branching in surveys so the question flow
     adapts based on user answers (single choice, multiple choice, likert).
     Users must be able to change earlier answers (with branched questions
     gracefully disappearing), save progress incrementally, and resume later. A
     final submit button is still required.

     The domain layer (BranchRule entity, DB schema, seed data) is already in
     place. The interface IQuestionnaireManager declares branching methods but
     they're unimplemented. The frontend is a linear vertical-scroll carousel
     with no branching awareness.

     Approach: Server-Driven Branching

     All questions are rendered in the DOM. The BL layer owns all branching 
     logic. The frontend is stateless beyond knowing which slide is currently
     displayed (inherent UI state from data-question-id). After saving an
     answer, the frontend makes a separate call to ask "what's next?" — the
     server evaluates branch rules against saved responses and returns the
     answer.

     IsCommitted on Response: Responses are never deleted. A bool IsCommitted
     field on Response defaults to false (interim save). On final submit, only
     responses for visible-path questions are set to IsCommitted = true.
     Half-filled questionnaires are preserved for analysis.

     Separation of Concerns: Saving responses and determining navigation are
     separate endpoints with separate responsibilities.

     2.1 QuestionnaireManager — Branching Logic

     File: BL/Implementation/QuestionnaireManager.cs

     All branching computation lives here. Implement the declared methods + new
     ones:

     - Update GetQuestionnaireByProjectIdAsync — change include from "Questions"
      to "Questions.BranchRules" so branch rules are always loaded.
     - GetFirstQuestionAsync(int projectId) — return first question by Position.
     - GetNextQuestionAsync(int currentQuestionId, int participantId) — load
     current question with BranchRules. Load saved response for this (question,
     participant) from DB. Evaluate branch rules against the saved answer (for
     MultipleChoice: split comma-separated answer, check if TriggerValue is
     among values). If match + SkipToEnd → return null (end of survey). If match
      → return TargetQuestion. Else → next question by Position in the same
     questionnaire. Note: the answer is read from the DB, not passed as a
     parameter — the server is the source of truth.
     - GetPreviousQuestionAsync(int currentQuestionId, int participantId) — walk
      the question path from the first question using saved responses,
     evaluating branch rules at each step. Return the question that immediately
     precedes the current one in the computed path. If current is the first
     question, return null.
     - GetQuestionCountAsync(int projectId) — count total questions.
     - ComputeVisiblePathAsync(int projectId, int participantId) — walks
     questions in Position order evaluating branch rules against the
     participant's saved responses. Returns List<int> of visible questionIds in
     order. Includes loop-detection guard. Used internally by submit to
     determine which responses to commit.
     - GetResumeQuestionAsync(int projectId, int participantId) — walk the
     visible path using saved responses. Return the first question that has no
     saved response (i.e., where the user left off).
     - Remove GetInvalidatedQuestionIdsAsync from the interface — no longer
     needed since responses are never deleted.
     - ValidateMandatoryAnswers — add HashSet<int> visibleQuestionIds param.
     Only validate mandatory questions in the visible set.

     Key Design Decisions

     1. All branching logic in BL — the frontend never computes which question
     comes next/previous. It asks the server, which reads saved responses from
     DB and evaluates branch rules.
     2. Separation of Concerns — saving responses (POST /responses) and
     navigation (GET /next-question, GET /previous-question) are separate
     endpoints with separate responsibilities.
     3. Stateless frontend — the only UI state is which slide is currently
     displayed (inherent to any carousel). All branching decisions come from the
      server.
     4. IsCommitted on Response — interim saves have IsCommitted = false. On
     final submit, visible-path responses get IsCommitted = true. Half-filled
     data preserved for analysis.
     5. No response deletion — when branches change, hidden responses stay in DB
      with IsCommitted = false. Only committed on final submit if in the visible
      path.
     6. Lazy session creation — participant created on first answer save, not on
      page load.
     7. MultipleChoice matching — TriggerValue is a single string. Split
     comma-separated answer, check if TriggerValue is among values.
