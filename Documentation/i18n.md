# Internationalisation (i18n)

This platform is fully bilingual: every participant-facing surface — interface
labels, validation messages, project content, and the AI flows (moderation,
writing assistance, speech-to-text) — is available in **Dutch (`nl`)** and
**English (`en`)**. Dutch is the default culture.

The hard part of internationalising this application is that the text on screen
comes from two very different owners, and each needs its own mechanism:

- **Static UI strings** — button labels, headings, error messages. These are
  written *by the developers*, are the same for every project, and ship inside
  the application. They belong in resource files.
- **Dynamic project content** — a project's name, introduction, categories,
  questions and answer options. These are written *by the admins* who set up
  each project, differ from project to project, and live in the database. They
  belong in translation tables.

Both tracks resolve against the same per-request *active culture*, so a Dutch
participant sees Dutch buttons *and* Dutch questions, and an English participant
sees both in English.

## The two-track model

| | Track 1 — Static UI strings | Track 2 — Dynamic project content |
|---|---|---|
| **What** | Buttons, headings, validation messages, error pages | Project name, introduction, categories, questions, answer options |
| **Authored by** | Developers | Project admins |
| **Stored in** | `.resx` resource files (compiled into the assemblies) | Database translation tables |
| **Same for every project?** | Yes | No — per project |
| **Resolved via** | `IViewLocalizer` / `IStringLocalizer` + active culture | Translation-row lookup keyed on the active culture |
| **Add a language by** | Adding a `.{culture}.resx` file | Adding a `Language` row + translation rows |

Both tracks read the **active culture** of the current request, which is
established once per request by the culture middleware (see below).

## Track 1 — Static UI strings (`.resx` resources)

### Resource files and their layout

Static strings live in `.resx` (XML resource) files — one file per language,
holding name/value string pairs. They exist in three projects:

```
UI-User/Resources/
  SharedResource.nl.resx / .en.resx        ← strings reused across many views
  Views/Survey/Scrollform.nl.resx / .en.resx   ← strings for one specific view
  Views/Shared/_Layout.nl.resx / .en.resx
  ... (one folder per controller, mirroring the view tree)
UI-Admin/Resources/                        ← same layout for the admin panel
  SharedResource.nl.resx / .en.resx
  Views/... / Models/...
BL/Resources/
  SharedResource.nl.resx / .en.resx        ← strings used by business-layer code
```

The folder path of a `.resx` file mirrors the namespace path of the type that
consumes it. `Views/Survey/Scrollform.{culture}.resx` backs the
`Views/Survey/Scrollform.cshtml` view; `SharedResource.{culture}.resx` is backed
by a marker class `SharedResource.cs` that exists in each project root.

### Referencing strings in views and code

Razor views inject a localizer and index it by key. `_ViewImports.cshtml`
imports `Microsoft.AspNetCore.Mvc.Localization` so every view can do this
without a fully-qualified type name:

```cshtml
@inject IViewLocalizer L                          @* per-view strings *@
@inject IHtmlLocalizer<SharedResource> Shared      @* cross-view strings *@

<h2>@L["SubmitSlideHeading"]</h2>
<button>@Shared["Submit"]</button>
```

`IViewLocalizer` is *view-aware*: `L["Title"]` in `Survey/Scrollform.cshtml`
resolves against `Resources/Views/Survey/Scrollform.{culture}.resx`.
`IHtmlLocalizer<SharedResource>` is *type-aware*: it always resolves against
`SharedResource.{culture}.resx`. If a key is missing, the localizer falls back
to the key text itself.

Business-layer and API code use the same mechanism through
`IStringLocalizer<SharedResource>` — see the validation-messages section below.

### Culture middleware — how the active culture is chosen

`UI-User/Program.cs` registers localization and configures how the active
culture is detected per request:

```csharp
builder.Services.AddLocalization(opts => opts.ResourcesPath = "Resources");

var supportedCultures = new[] { "nl", "en" };
builder.Services.Configure<RequestLocalizationOptions>(opts =>
{
    opts.SetDefaultCulture("nl")
        .AddSupportedCultures(supportedCultures)
        .AddSupportedUICultures(supportedCultures);

    opts.RequestCultureProviders =
    [
        new CookieRequestCultureProvider(),
        new AcceptLanguageHeaderRequestCultureProvider()
    ];
});
```

For every request, `app.UseRequestLocalization(...)` runs the providers in
order and uses the first that yields a supported culture:

1. **Cookie** (`CookieRequestCultureProvider`) — reads the `.AspNetCore.Culture`
   cookie. This is the participant's explicit choice and takes priority.
2. **`Accept-Language` header** (`AcceptLanguageHeaderRequestCultureProvider`) —
   the browser's language preference, used on a first visit before any choice
   has been made.
3. **Default culture** (`nl`) — when neither yields a supported value.

The result is stored in `CultureInfo.CurrentUICulture` for the duration of the
request, and that is what both `.resx` lookups and database-translation lookups
read. The default `QueryStringRequestCultureProvider` is deliberately *not*
registered, so the culture cannot be forced through the URL.

The same wiring exists in `UI-Admin/Program.cs` (for the admin panel) and in
`API/Program.cs` — the API registers only the `Accept-Language` provider,
because it has no cookie of its own (see *AI flows* below).

### `<html lang>` per request

`_Layout.cshtml` sets the document language from the active culture so
assistive technology announces the page in the correct language:

```cshtml
<html lang="@CultureInfo.CurrentUICulture.TwoLetterISOLanguageName" ...>
```

### Localised validation messages

Validation errors are localised too. The business layer never throws a
hard-coded English message; instead it throws a `LocalizedValidationException`
carrying a *stable error code* (and optional format arguments):

```csharp
throw new LocalizedValidationException("Validation.Project.DefaultLanguageMustBeSupported");
throw new LocalizedValidationException("Validation.Language.UnknownCodes", string.Join(", ", missing));
```

The API's `ExceptionHandlerMiddleware` catches it, looks the code up against
`BL/Resources/SharedResource.{culture}.resx` via `IStringLocalizer<SharedResource>`
in the request's culture, and returns a `400` with the translated message. If
the code has no resource entry, the code string itself is returned as a
fallback. This keeps the business layer free of presentation strings while
still producing Dutch or English error text.

### Frontend (TypeScript) strings

The browser cannot read `.resx` files, so the server pre-renders the strings
the TypeScript code needs into a global object. `_Layout.cshtml` emits, inside
`<head>` and *before* the script module loads:

```cshtml
<script>
  window.__i18n = {
    culture: @Json.Serialize(CultureInfo.CurrentUICulture.Name),
    strings: @Json.Serialize(new {
      submit = Shared["Submit"].Value,
      cancel = Shared["Cancel"].Value,
      // ~65 more keys consumed by the TypeScript modules
    })
  };
</script>
```

`UI-User/src/lib/i18n.ts` declares the shape of that object and exposes a typed
accessor:

```ts
export const t = <K extends keyof Strings>(key: K): string => window.__i18n.strings[key];
export const currentCulture = (): string => window.__i18n.culture;
```

TypeScript modules then call `t('speechToTextUnavailable')` for a synchronous,
compile-time-checked string lookup — no fetch, no async, no loading state. The
culture is fixed at page render, so switching language requires a full page
reload.

## Track 2 — Dynamic project content (database translations)

Project content is authored per project and per language by admins, so it
cannot live in `.resx` files. It lives in the database, modelled around a
central `Language` lookup and one *translation table* per translatable entity.

### The `Language` entity

`Domain/I18n/Entities/Language.cs` is the global lookup table:

```csharp
public class Language
{
    [Key] [MaxLength(10)] public string Code { get; set; }        // "nl", "en"
    [Required] [MaxLength(50)] public string DisplayName { get; set; }
    public bool IsActive { get; set; } = true;                    // soft on/off switch
}
```

`Code` is the primary key (a BCP-47 culture code). `IsActive` lets an
administrator retire a language without deleting it.

### The translation-table pattern

Every entity that carries admin-authored display text keeps its
language-independent data (IDs, foreign keys, numeric settings) on the original
entity, and moves its translatable text into a sibling *translation* entity. A
translation row is identified by the **(parent entity, language)** pair and
holds one language's version of the text.

```csharp
// Domain/Project/Entities/ProjectTranslation.cs — child of Project
public class ProjectTranslation
{
    [Required] public Project Project { get; set; }              // composite key part 1
    [Required] public Language Language { get; set; }            // composite key part 2

    [Required] [MaxLength(100)] public string Name { get; set; }
    [MaxLength(100)] public string Topic { get; set; }
}
```

The composite key `(ProjectId, LanguageCode)` is configured with EF Core's
Fluent API in `SynapseEnqueteContext.OnModelCreating` — the foreign-key columns
are EF *shadow properties*, so no database concerns leak into the domain class:

```csharp
builder.Entity<ProjectTranslation>(e =>
{
    e.Property<int>("ProjectId");
    e.Property<string>("LanguageCode").HasMaxLength(10);
    e.HasKey("ProjectId", "LanguageCode");
    e.HasOne(t => t.Language).WithMany()
        .HasForeignKey("LanguageCode")
        .OnDelete(DeleteBehavior.Restrict);   // a language in use cannot be deleted
});
```

The same shape repeats for the whole project aggregate. All six translation
entities live in `Domain/Project/Entities/`:

| Translation entity | Parent | Translated fields |
|---|---|---|
| `ProjectTranslation` | `Project` | `Name`, `Topic` |
| `IntroductionTranslation` | `Introduction` | `Text` |
| `CategoryTranslation` | `Category` | `Name`, `Description` |
| `SectionTranslation` | `Section` | `Name`, `Description` |
| `QuestionTranslation` | `Question` | `Text`, `AnswerChoices`, `MediaText` |
| `EndingAnswerTranslation` | `EndingAnswer` | `Value` |

`QuestionTranslation.AnswerChoices` is an *ordered* list of strings: each
language stores the option labels in the same order, so branching logic can
refer to an option by position rather than by translated text.

### How a project records which languages it supports

The `Project` entity gains three language-related members:

- `DefaultLanguage` — the project's primary language (FK `DefaultLanguageCode`,
  `OnDelete: Restrict`). Used as the fallback when a translation is missing.
- `SupportedLanguages` — a many-to-many set of `Language`, stored through the
  `ProjectLanguage` join table. These are the languages offered to participants.
- `Translations` — the collection of `ProjectTranslation` rows.

Participant submissions (`Idea`, `Comment`, `Response`) are *not* translated —
they are stamped with the `LanguageCode` they were written in, because they
already exist in exactly one language.

### `TranslationUpserter` — creating and updating translations

When an admin saves a project, the set of translation rows must be
reconciled with the submitted set: new languages added, existing ones updated,
removed ones deleted. `BL/Implementation/TranslationUpserter.cs` is a generic
helper that performs this reconciliation for any translation type:

```csharp
internal static class TranslationUpserter
{
    public static void Upsert<TTranslation, TInput>(
        ICollection<TTranslation> existing, IEnumerable<TInput> inputs,
        Func<TInput, string> inputLanguageCode,
        Func<TTranslation, string> existingLanguageCode,
        Func<TInput, TTranslation> create,
        Action<TTranslation, TInput> update)
    {
        // 1. remove every existing row whose language is not in the input set
        // 2. for each input: update the matching row, or create a new one
    }
}
```

`ProjectManager` and `CategoryManager` call it from their `Update...` methods,
passing closures that map between the input records and the EF entities. On
*create*, the managers add the translation rows directly.

### Retrieving the right translation

There is no automatic translation fallback in EF; the application resolves it
explicitly. The pattern, used in `API/Controllers/ProjectsController.cs`, is
**active culture → project default language → first available**:

```csharp
private static ProjectTranslation ResolveTranslation(Project p)
{
    var active = CultureInfo.CurrentUICulture.TwoLetterISOLanguageName;
    return p.Translations.FirstOrDefault(t => t.Language?.Code == active)
        ?? p.Translations.FirstOrDefault(t => t.Language?.Code == p.DefaultLanguage?.Code)
        ?? p.Translations.FirstOrDefault();
}
```

So a participant always sees *something* — their own language if it exists, the
project's default language otherwise, and only the first available row in the
(invalid) case where neither is present. The same three-step fallback is used
for introductions, category names (`CategoryManager.ResolveCategoryName`), and
project content in the social-media flow.

### Language validation on create / update

A regular manager owns one repository; `ProjectManager` and `CategoryManager`
are granted an extra `ILanguageRepository` dependency specifically so they can
validate language codes. `ProjectManager.ValidateTranslationInputsAsync`
enforces, before any write:

- a default language code is provided;
- at least one supported language is listed;
- the default language is among the supported languages;
- there is exactly one translation row per language (no duplicates);
- every supported language has a translation row;
- every referenced code exists in the `Language` table and is `IsActive`.

`CategoryManager.ValidateTranslationInputsAsync` additionally checks that a
category supplies a translation for every language its parent project supports.
Violations throw a `LocalizedValidationException`, which surfaces to the admin
as a localised `400` (see Track 1).

`LanguageManager` (with its own `ILanguageRepository`) exposes read-only lookups
— `GetByCodeAsync`, `GetAllActiveAsync`, `GetByCodesAsync` — for code that just
needs to read the language list.

### Missing-translation behaviour

Because validation guarantees every supported language has a translation row,
a missing translation is not expected in normal operation. If one is missing
anyway, the resolution fallback above silently degrades to the project's
default language, then to the first row — the participant never sees an empty
field or a crash.

## Participant language preference

### Switching language — the header pill

Every page header carries a segmented-pill language switcher (`_Layout.cshtml`).
It is a POST form, one button per supported culture, with `aria-current="true"`
on the active one:

```cshtml
<form asp-controller="Culture" asp-action="SetCulture" method="post" ...>
    <input type="hidden" name="returnUrl" value="@(Context.Request.Path + Context.Request.QueryString)" />
    @foreach (var c in LocalizationOptions.Value.SupportedUICultures ?? [])
    {
        <button type="submit" name="culture" value="@c.Name"
                aria-current="@(isActive ? "true" : "false")">@c.TwoLetterISOLanguageName</button>
    }
</form>
```

### Where the preference is stored

The preference is recorded in **two places**:

1. **A cookie** — `CultureController.SetCulture` validates the chosen culture
   against the supported set, then writes the `.AspNetCore.Culture` cookie
   (one-year expiry, `IsEssential`, `Secure` on HTTPS). This cookie is what the
   culture middleware reads on the next request.
2. **The database** — the `Participant` entity has a `Language` navigation
   property. `CultureController` finds every `ParticipantToken_{projectId}`
   cookie the visitor holds and calls `ParticipantService.SetLanguageAsync` for
   each, persisting the choice so it survives a cleared culture cookie and so
   the API can read it server-side.

`ParticipantManager.SetLanguageAsync` validates that the requested language is
a known, active `Language` before assigning it to the participant.

### `ParticipantLanguageCoordinator`

Switching language is not a single-table write — when a participant changes
language, their already-submitted survey answers should follow. That
cross-manager use case is a *coordinator* (a manager with no repository of its
own that composes other managers):

```csharp
public class ParticipantLanguageCoordinator(
    IParticipantManager participantManager,
    IResponseManager responseManager) : IParticipantLanguageCoordinator
{
    public async Task SwitchLanguageAsync(int participantId, string languageCode, CancellationToken ct = default)
    {
        var newLanguage = await participantManager.SetLanguageAsync(participantId, languageCode, ct);
        await responseManager.RetranslateResponsesForLanguageAsync(participantId, newLanguage, ct);
    }
}
```

`RetranslateResponsesForLanguageAsync` walks the participant's responses and,
for choice-type answers, maps each stored value to the equivalent label in the
new language (using the question's `AnswerChoices` translations) and re-stamps
the response's `LanguageCode`.

### How the preference reaches the API and the AI

UI-User talks to the API over HTTP. To carry the active culture across that
boundary, `CultureForwardingHandler` — a `DelegatingHandler` registered on
*every* outbound `HttpClient` — adds the current culture as an `Accept-Language`
header on each request:

```csharp
public class CultureForwardingHandler : DelegatingHandler
{
    protected override Task<HttpResponseMessage> SendAsync(HttpRequestMessage request, CancellationToken ct)
    {
        var culture = CultureInfo.CurrentUICulture.Name;
        if (!string.IsNullOrEmpty(culture))
            request.Headers.AcceptLanguage.TryParseAdd(culture);
        return base.SendAsync(request, ct);
    }
}
```

The API's `AcceptLanguageHeaderRequestCultureProvider` reads that header and
sets `CurrentUICulture` for the API request — so the API resolves translations,
validation messages, and AI-prompt languages in the participant's chosen
language without needing its own cookie.

## AI flows in the participant's language

A Dutch participant must never receive English AI feedback. Every AI flow is
therefore parameterised by language, and the language is the participant's
active culture (delivered to the API via the `Accept-Language` header above).

### Moderation

`AiModerationService` does not hard-code a language into its prompts. The
moderation, comment-moderation, image-moderation and rewrite prompts contain a
`{response_language}` placeholder that is substituted at call time:

```csharp
var prompt = rawPrompt.Replace("{response_language}",
    respondInLanguage ?? platformConfig.Moderation.DefaultLanguage,
    StringComparison.OrdinalIgnoreCase);
```

The controllers pass `CultureInfo.CurrentUICulture.TwoLetterISOLanguageName` as
`respondInLanguage` (for example in `IdeasController` and `CommentsController`),
falling back to the platform's configured default language if it is absent. The
LLM is thus told, per request, which language to phrase its feedback in.

### Idea and comment writing assistance

`AiIdeaSupportService` and `AiCommentSupportService` substitute a `{language}`
placeholder into their system prompts *and* append an explicit, unambiguous
instruction built from the full language name:

```csharp
var langName = GetLanguageName(request.Language);   // "Dutch" / "English"
// ... "Respond only in <langName>. Do not use any other language."
```

`GetLanguageName` resolves the code to its English display name via
`CultureInfo.GetCultureInfo(langCode).EnglishName`. Naming the language in full
keeps the instruction unambiguous regardless of the language the base prompt
itself is written in.

### Speech-to-text

`AiSpeechToTextService` passes the language into the transcription prompt so the
model transcribes in the correct language. The controllers take the language
from the request body if supplied, otherwise from the active culture:

```csharp
var lang = string.IsNullOrWhiteSpace(dto.Language)
    ? CultureInfo.CurrentUICulture.TwoLetterISOLanguageName
    : dto.Language;
```

This matters because a Dutch utterance transcribed under an English model would
be garbled — the culture must follow the audio.

## Admin and platform content

Admins author **all languages of a project at once**, not one language at a
time. The create/update DTOs carry the full set of translations together:

```csharp
public record CreateProjectDto
{
    [Required] [MaxLength(10)] public string DefaultLanguageCode { get; init; }
    [Required] [MinLength(1)] public ICollection<string> SupportedLanguageCodes { get; init; } = ...;
    [Required] [MinLength(1)] public ICollection<ProjectTranslationDto> Translations { get; init; } = ...;
    // language-independent fields: ShortForm, ImageUrl, ages, page sizes, Theme, ...
}
```

`ProjectTranslationDto` and `CategoryTranslationDto` are the per-language
payloads — one DTO instance per language, each carrying that language's text:

```csharp
public record ProjectTranslationDto
{
    [Required] [MaxLength(10)] public string LanguageCode { get; init; }
    [Required] [MaxLength(100)] public string Name { get; init; }
    [MaxLength(100)] public string Topic { get; init; }
    [MaxLength(5000)] public string Introduction { get; init; }
}
```

`AdminProjectDto` (the read DTO) exposes the *whole* `Translations` collection
so the admin UI can present an editable field per language. This is the key
contrast with the participant-facing `ProjectDto`, which is *already resolved*:
the server picks the one right translation (active culture → default → first)
and flattens it into plain `Name` / `Topic` / `Introduction` strings, plus a
`LanguageCode` telling the frontend which language those strings are in. The
participant frontend therefore never has to choose a translation — it just
renders.

The UI-Admin panel localises its own chrome through the same `.resx` mechanism
as UI-User, with its own `Resources/` tree and its own `SharedResource` marker
class.

## Known gaps

- **Per-element `lang` attribute.** `<html lang>` is set per request, but
  mixed-language content *within* a page (for example an English quotation on
  an otherwise-Dutch page) is not marked up with a per-element `lang`
  attribute. This is a known accessibility gap (WCAG 3.1.2 *Language of Parts*),
  tracked as low severity in the accessibility documentation.
- **Supported cultures are hard-coded.** `UI-User/Program.cs` lists the
  supported cultures as a literal `{ "nl", "en" }` array rather than loading
  them from the `Language` table at startup. Adding a third language therefore
  currently requires a code change in addition to the data change. This is
  flagged with a `TODO` in `Program.cs`.
- **Language switch requires a full page reload.** Because the TypeScript
  strings are baked into the page at render time, switching language reloads
  the page rather than re-rendering in place. This is an intentional
  simplicity trade-off, not a defect.
